# Enrolled schedule qualification

This is repair family six. A background job can make an important query wait even when the query itself is well designed. Pooltune may move future executions into an explicitly allowed quiet period. It must preserve the job's work, frequency and deadline. Finishing the schedule change is not the same as proving it helped.

## Prespecified staging scope

Jared approved enabling Supabase Cron on Rookery on November 14. The `enable_pooltune_staging_cron` migration installed pg_cron 1.6.4. The readback found zero existing jobs. Do not remove the extension during cleanup or change any unrelated job. Create one uniquely named Pooltune target job and one diagnostic witness job, pin their IDs/owners/databases/commands and record the target's original schedule durably. The initial one-job draft was extended after the builder check found that wall-clock time and empty running history do not prove scheduler progress.

Use two-minute test cycles in UTC. The original schedule is `*/2 * * * *`; the offered alternative is `1-59/2 * * * *`. Each cycle requires exactly one successful execution before the next even minute. The important query's busy period is the first 20 seconds of the even minute. The odd minute is the explicitly declared quiet window for this synthetic application. These are test-owner constraints, not guessed customer deadlines.

The private job models lock contention on the owned candidate table. Its pinned procedure may use short, bounded locks separated by transaction commits, with a total duration below 20 seconds. Start with 200 holds of 80 ms, each in its own transaction. The target query continues at two calls/second in measured affected/control periods; healthy reads and value-changing healthy-table writes continue at four and two/second. The short hold must stay below the existing request timeout. Cap the procedure's total lifetime and set lock timeouts; never lock application tables. Record the actual selected constants before running. If this fixture does not produce the required evidence, report that failure and revise the fixture explicitly instead of lowering the evidence threshold.

For each two-minute cycle, target calls occur in the even minute's first 20 seconds and its matched control period at seconds 30–50. The declared quiet odd minute has no target calls, before or after rescheduling; healthy reads/writes continue throughout and are measured during the moved job. This models an owner-approved quiet period rather than hiding target regressions by changing offered demand after the repair. Keep the witness active across both monitoring-off/on comparisons and report its work separately where identifiable.

The procedure may take a bounded hold-count argument in 1–200, with the actual job command permanently pinned to 200. The brief-spike probe can invoke the same procedure directly with 30 holds (about 2.4 seconds); label it manual fault setup, not an observed scheduled execution. All three original and future execution requirements use the actual Cron job's full 200-hold command. Pin the argument signature and command along with the body. The read-function objective freezes before faults from ten clean samples as max(3 ms,1.5 times measured database mean); this is the synthetic enrollment objective, not a release default.

This is an intentionally induced lock-contention workload, not a claim about representative customer CPU jobs. Attribute blocking to the exact enrolled job backend and backend start, alongside pg_cron execution history. Coincident timing alone is insufficient.

The enrolled read is an outer call to a pinned PL/pgSQL security-invoker function that reads the candidate table. Its executor includes the inner query's lock wait, which a direct table query's execution-only counter can miss. Pin both routine identities and the outer query identity; verify this timing boundary locally before the long run. Measure the outer query through the existing detector counters. The function is not a repair target in this case.

The job command is one top-level `CALL`. Its committing procedure must be security-invoker, have no declaration-level SET clause and no enclosing exception block. Use a real elapsed-time failure guard and bounded per-lock waiting. Check inherited job-session limits and actual completion of all 200 iterations; returning early cannot count as successful required work. No role-wide or server-wide timeout changes are authorized.

## Evidence and acceptance

Observe three original scheduled executions and three matched job-free control periods, with at least 20 target calls in each period and unchanged offered demand. Each affected period must show at least 30% and 20 ms extra mean latency, with measured contention and successful required job execution. Preserve counter generations and role/query identity. Store selected measurements durably so the consumer can inspect them; no fabricated model evidence or manual recommendation injection.

After those periods, the shared investigator must make a real Claude call. Its typed proposal can choose the enrolled alternate window or no change. Go independently checks identity, current schedule, allowed window, required frequency/deadline, absence of an active/queued duplicate and current conditions. It changes only the schedule. Do not rewrite the command or cancel a running job as the repair.

Apply after the current cycle's odd-minute boundary has passed, with a declared guard margin, so the already-completed even-minute run is not duplicated by a new odd-minute run in that same cycle. Refuse a late or ambiguous handoff. Record the first eligible future execution and cycle boundaries before changing the schedule. Across three future executions, verify exactly one completed run per cycle by its deadline, matched foreground benefit of at least 20% and 5 ms above the noise gate, and no measured harm to the quiet-window healthy traffic. Missed/duplicate work or missing history cannot count as success.

Create the target inactive and activate it in a recorded interval that does not cross a due boundary. Account for every expected execution since activation and require complete successful history, with no active work, before handoff. Missing history or an overdue run refuses the change. Empty active history alone cannot exclude pending scheduler work.

The fixed witness command is `SELECT 1`, scheduled every two seconds. Before mutation, require two distinct successful witness executions whose actual starts are strictly after the passed odd-minute boundary. After the acknowledged schedule commit, require two more distinct successful starts strictly after that commit time. Both proofs must finish at least 15 seconds before the next even minute. Use target database time, unchanged launcher/backend generation, complete history and unchanged witness identity. Refuse action if its precondition is missing; missing post-action proof remains uncertain and cannot trigger a blind repeat. A single late witness is insufficient.

This witness is a source-based inference for the private fixture: pg_cron 1.6.4 processes invalidations and refreshes its cache before calculating pending runs, then manages their execution. One witness can belong to a prior iteration; two distinct starts establish subsequent progress. The post-commit check guards a scheduler paused with the old schedule cached. Test those interleavings, an already queued witness, a delayed second witness, restarts, clock ambiguity and expired margins. This is not a general production scheduler guarantee. See the [pinned launcher loop](https://github.com/citusdata/pg_cron/blob/v1.6.4/src/pg_cron.c#L598-L630).

## Durable delayed verification

The existing consumer bounds each claim to 25 seconds. Keep that bound. Waiting for several real scheduled executions belongs in durable state, not a long-running model call or a sleeping worker claim.

Add an explicit not-before time to the existing queue, defaulting to immediately eligible for existing repairs. After applying the schedule, atomically finish the initial claim with `awaiting_verification` and create one uniquely associated follow-up claim due after the three required execution windows. Preserve the original investigation/action link. The existing unique unfinished-query rule must still prevent duplicate follow-ups; queue transitions must occur under the existing project lock and verify claim ownership. A future claim must not prevent other due queries from running. Tests must cover competing consumers and restart before the due time.

If the detector queues an incident before three complete affected/control periods exist, use the same atomic continuation with `awaiting_evidence`. Do not turn temporary incompleteness into a terminal decline and cooldown. Only complete evidence in an eligible handoff window reaches Claude. Preserve action-recovery discovery even if the ordinary queue exhausts its two attempts; retry exhaustion must not hide an uncertain external action. Missing traffic periods after restart remain missing, even if all scheduled jobs succeeded.

The follow-up inspects the journal, pinned job and measured periods, verifies the result without another model decision or another schedule mutation, and records the final outcome. Pending-action recovery first inspects the current schedule. It must not blindly repeat `alter_job`, overwrite an independent setting, or label a pending outcome verified. Persisted intent and conditional queue transitions must survive a crash between target mutation and state acknowledgement. A confirmed regression can restore only the unchanged Pooltune-applied schedule, subject to the same no-duplicate/deadline checks; otherwise report the conflict for review.

## Measurements and limits

Report detection/evidence accumulation, queue delay, Claude time, schedule-action time and future-cycle verification separately. A several-minute outcome check is expected because the job must actually execute three times. Do not include fixture construction in incident-to-action latency or imply the entire cycle wait was model latency.

Extend the existing traffic driver and reporting helpers, including short-spike rejection, monitoring comparisons, errors, missed request slots, process recovery and owned-object cleanup. The cron scenario needs a longer wall-clock budget than the query-repair scenarios. Persist creation intent before either Cron job and retain ownership discovery after acknowledgement loss. Confirm terminal work before unscheduling, with a boundary margin, because unscheduling running work can cancel it. Remove only the recorded test jobs and private objects; preserve unknown identity/state for recovery. Preserve unrelated jobs and extension setup.

The strongest simpler alternative is changing a schedule and immediately reporting success. That is faster to demonstrate but cannot establish that required work still happens or that contention moved safely. This design pays the real observation time once and keeps the service's individual work steps short.

References: [pg_cron](https://github.com/citusdata/pg_cron), [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart).

## Local implementation contract

The implementation adds `cron_policy.go`, `cron_fixture.go`, `cron_periods.go`, `cron_cleanup.go`, `queued_cron.go`, and the shared `queue_continuation.go`. The investigator keeps one graph and provider adapter. `cron-schema.ts` holds the typed evidence screen, and `cron-traffic.ts` holds the operation-specific timeline. It reuses the shared request, counter-delta, traffic-summary, diagnostic-filter and timing helpers from `traffic.ts`.

The read is `SELECT <private schema>.pooltune_cron_read() AS id`. It returns the enrolled primary-key row 43 through PL/pgSQL. The model envelope uses the actual outer EXPLAIN `Result` node, with no invented measured scan counts; the cause is stored separately in Cron periods. Local PostgreSQL verified that an induced 100 ms inner lock wait appears in the outer execution counter. This is a real PostgreSQL timing test, not pg_cron qualification.

The fixed scheduled command is one top-level `CALL <private schema>.pooltune_cron_hold(200)`. The procedure takes 200 independently committed 80 ms locks, uses 150 ms transaction-local lock timeouts, checks elapsed time before each lock and after all work, and fails if it reaches 19 seconds. It has no declaration-level SET, SECURITY DEFINER or enclosing exception block. An inherited statement timeout below 20 seconds is refused before work; fixture setup records the observed inherited timeout and execution mode. No timeout is changed at role/database/server scope. A full local 200-hold call completed in 16.40839 seconds. The pinned procedure refuses new work after its 25-minute fixture expiry. This bounds induced lock work; it does not automatically remove its recurring catalog entry or the diagnostic witness after a process crash.

Both jobs are created inactive in one target transaction, after durable creation intent. The witness can be activated first for the reversed monitoring comparisons. Target activation requires the odd minute at seconds 5 through 39, records the next even first cycle before activation, and records acknowledgement before the 15-second boundary margin. An uncertain activation remains in the journal for explicit recovery. Exactly matched measurements contain 40 offered target requests in each busy/control slot, 80 healthy reads and 40 changing healthy-table writes in every measured 20-second slot, and zero target demand in the odd quiet slot. Go verifies counter identities/generations, actual query IDs, nonnegative deltas, errors/misses, period times and pinned blocking/run identities before retaining a period.

The first detector incident is completed as `awaiting_evidence`, with a uniquely linked child due at the end of the third original quiet observation plus two seconds. This is a pending incident, not a terminal decline/cooldown. The model is admitted only with all three complete periods, complete successful target lifetime history, a stable launcher generation, two later successful witness starts and time for the guarded handoff. The original/alternate expressions, one run per cycle and next-even deadline remain fixed. A late handoff refuses mutation; it does not invent a new window.

The schedule-only mutation records intent before the target transaction commits. Pre-action proof is rechecked under the job row lock. After acknowledgement, two successful starts strictly later than that target-database timestamp must arrive within eight seconds and before the fixed margin. Missing acknowledgement/proof remains discoverable as a pending action; recovery reads the actual schedule and never repeats the model or mutation. The normal 25-second claim and 30-second lease remain. Parent completion and a unique delayed child happen atomically under the project lock. A future child is excluded before selecting due work. Retry exhaustion cannot hide `cron_pending` or `cron_verifying` actions: independent reconciliation intake creates an inspection continuation from the final exhausted child. Final verification waits until all three future cycle deadlines have passed. Missing foreground/healthy periods stays inconclusive even when job history is complete.

Regression or uncertainty is retained for review and owned fixture cleanup. This staging implementation does not attempt a second schedule change to restore the original expression: doing that safely would require another qualified handoff. It never silently overwrites an independent schedule.

## Cleanup ruling and recovery

The initial draft required every owned run to be terminal before unscheduling. Source review showed why a two-second witness creates a fragile stop window: pg_cron can retain a pending interval run while connecting, and a successful recent start alone does not establish an empty pending queue. The controller selected a narrower fixture-specific rule under the existing authority to create/remove Pooltune test jobs and stop Pooltune's own diagnostic work: **only the exact owned fixed `SELECT 1` witness may be unscheduled while active during cleanup**. It has no application payload or completion deadline. A canceled witness is never scheduler-progress proof. This is an internal test ruling, not new customer cancellation authority.

The target job still requires complete lifetime accounting, terminal history, stable generation, later witness proof, and at least 15 seconds before its next due boundary. Cleanup validates the exact IDs/names/owners/databases/commands and routine definitions. It archives target history before unscheduling, removes both jobs transactionally, then waits for terminal history and absence of their identified backends before dropping owned routines/tables with RESTRICT. Foreign or changed jobs/routines remain for review. No unrelated jobs or extension settings are removed.

Explicit crash recovery uses the same bound target/state configuration and journal discovery, including creation acknowledgements lost before the driver knew the ID:

```sh
pooltune-query-lab -target rookery -cron-action recover
```

Recovery may refuse while target work is active or outside its safe boundary interval. Retry within the next eligible interval; do not manually cancel the target job. A particular known fixture can use `-remove-consumer-fixture <24-hex-id>`. Unknown identity, incomplete lifetime history or generation changes remain visible instead of being forcibly removed. Operators must resolve such retained fixtures before another qualification; the procedure's expiry stops additional induced lock work, while its catalog entry and witness remain durably tracked.

Other private harness interfaces are `-create-consumer-fixture -cron-fixture`, `-cron-action witness -cron-id <id>`, `-cron-action activate -cron-id <id>`, `-cron-action inspect -cron-id <id>`, and `-cron-action record -cron-id <id> -cron-period <selected-period.json>`. Period recording is a trusted private harness input, not a public customer telemetry API. It carries actual selected counter snapshots and blocking observations; production provenance/authentication remains unqualified.

Run the hosted scenario with `node investigator/traffic.ts cron`. It retains a 20-minute work budget and up to three minutes for bounded cleanup attempts; the enclosing launcher should allow 25 minutes. It prints phase progress, writes a complete report on success/failure, records Claude/action/future-cycle timing separately, and actually restarts only the consumer process while the verification child is still future-dated. The report path defaults to the temporary directory and can be fixed with `POOLTUNE_CRON_REPORT_PATH`. Setup/alignment and transport time remain distinct from database execution measurements. Snapshot/attribution traffic is not a total diagnostic CPU measurement.

Local catalog-adapter tests deliberately do not emulate pg_cron's scheduler. They test changed owners/commands/database/schedule/routines, creation acknowledgement loss, preservation of foreign jobs, interrupted action recovery, delayed queue ownership/restart and final replay. Actual pg_cron execution mode, scheduler witness timing, complete original/future cycles, full protected traffic and a real Claude decision remain mandatory hosted checks before declaring this repair qualified. The pinned source-based witness inference remains private-fixture evidence, not a general production scheduler guarantee.

## Fresh review corrections, fix round 1

Fresh review identified an activation gap in the initial implementation: wall time in an odd minute did not prove that a paused launcher had processed the prior even minute. The controller's recorded ruling strengthens this private-fixture precondition. Before activation, the target must still be inactive with no execution history, and the already active owned witness must show two distinct successful starts strictly after the current odd boundary. The proof and launcher generation are retained in the fixture journal. Job row locks, a repeated identity/time/generation check and the existing acknowledgement margin surround target activation. Missing proof refuses before writing activation intent. The prior wall-time-only implementation remains in commit `2b52e7b`; schedules, work counts and deadlines are unchanged. A catalog-adapter interleaving test demonstrates the stalled-launcher counterexample and refusal until later witness progress exists. It does not claim to run pg_cron.

Cleanup now validates both enrolled routines and the relevant table/schema identities inside the target transaction before unscheduling either job. A changed procedure body/owner or read-function settings/owner, or changed table ownership, preserves both job rows and the changed objects. The owned diagnostic witness exception remains unchanged. The later routine/table removal still repeats its existing checks.

The traffic driver attaches rejection handlers immediately for manual spike, activation and period-record work, and waits for both the operation and its parallel traffic to settle before cleanup can close clients. Its observer and traffic lanes use the same settlement boundary. Separate Node subprocess tests require a saved failed report and attempted owned cleanup after immediate failures; they exercise the production phase, cleanup and report functions with controlled operation callbacks, not a hosted database.

Schema removal alone no longer establishes successful cleanup. The driver sets `cleanup_verified` only after owned-job absence and unrelated-job/public-index readbacks all pass. Every loop exit requires that flag, including deadline and attempt exhaustion. Incomplete verification records `cleanup_failed`, the fixture recovery ID and the last failure capped at 400 characters, and forces `passed=false`. The regression covers deadline exhaustion after schema removal while preservation readback remains unavailable.
