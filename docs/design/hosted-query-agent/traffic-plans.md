# Measured plans from ordinary enrolled traffic

Task 40 adds a second plan source to the current read-only investigation. PostgreSQL's existing `auto_explain` module measures queries the application actually runs. An owner enables it on an explicitly chosen login in the target database and separately grants access to a specific enrolled query ID. Railway looks for measured evidence only during a claimed slowdown job and only for that exact database, login and query ID. The detector uses its usual workload counters. No query runs a second time.

The strongest alternative was an application-side plan callback. Supabase's role-level logging can measure normal parameterized calls without a code change or independent collector in the app. The tradeoff is Supabase log access and role-wide logging during the opt-in period. The raw Supabase entry can include SQL and plan predicates even with separate parameter reporting disabled. A ClickHouse projection selects only bounded plan metric fields. Pooltune receives no statement text, filters, relation names or bind values. Use a temporary project-scoped Logs Read token in staging. A token with these permissions can technically access other logs in that project. The code always sends a fixed projection with exact role and statement filters.

The first qualification covers a single-table lookup with two predicates and an ordered range with a limit. The evidence describes the measured root and at most its first child, with actual and estimated root rows, optional filter count, shared buffers and duration. Other eligible root shapes may supply evidence, but the Rookery proof covers only these two. Source logging must use JSON, actual row and buffer collection, per-node timing off and nested logging off. The owner chooses a duration and sample rate. Capture changes only the selected test role. Enable logging only where the owner approves the raw Supabase log contents and overhead. Login attribution requires a direct login role matching the enrolled role. The reader requires a nonprivileged, dedicated login with direct grants and no role memberships. Preserve that restriction throughout capture. Withdraw and regrant access before changing role membership or switching roles. The request matches the primary host and project identifier reported by Supabase. Replicas, pooled and Data API sessions are outside this qualification.

A sample must be at most two minutes old and no earlier than the grant or the current PostgreSQL counter generation. Grant, identity and detector objective are checked after fetching, at model admission and before publishing. A plan already admitted to graph processing can remain in internal checkpoints after later revocation. The selected sample stays bound to the job during those checks. The plan is historical evidence of one ordinary execution. A newer plan can differ. Source failure or an unsupported sample falls back to the existing passive or owner-captured lookup path where available. A plan-only job gets one queued retry after 20 seconds for delayed log delivery, then ends with insufficient evidence if no usable sample arrives. The delay does not occupy the worker. The separate traffic-plan path supplies no table maintenance or usable-index claims, and gives Sonnet no evidence tools or repair authority.

## Enable and revoke in staging

Run `pooltune-project setup-traffic-plan-sql -ref "$PROJECT_REF" -key "$INSTALLATION_KEY"` and apply its output using the same database owner that installed the monitor. Enroll the exact statement counter before inserting its `role_oid`, signed `query_id`, owner-selected `context_table` and positive `context_column` in the installation's `traffic_plan_grants`. The table and column bind the investigation and preserve the existing graph identity contract. They are never interpreted as an index candidate or plan relation.

Set `auto_explain.log_min_duration` and `auto_explain.sample_rate` for the chosen login in `postgres`. Set `log_format=json`, `log_analyze=on`, `log_buffers=on`, `log_timing=off`, `log_nested_statements=off`, `log_level=log`, and `log_parameter_max_length=0` on the same login using the `auto_explain.` prefix. Use bound parameters and open new sessions to pick up those settings. Removing bind logging does not redact a plan predicate. Scope settings to the opt-in role and database. In Railway, provide `POOLTUNE_PROJECT_LOGS_TOKEN` privately to the enrolled service as a fine-grained Supabase token limited to the same project and Logs Read.

Delete the grant to stop eligibility for the next check, and reset the logging settings on that role and close its instrumented sessions to stop capture. Remove and revoke the token when no enrolled statements use the source. Previously emitted provider logs follow Supabase's retention policy.
