Use Superpowers executing-plans inline. User explicitly approved the app-through-Pooltune architecture and asked to build and run short spike tests, without another approval round.

Goal: respond to short traffic spikes using already established, budgeted connections instead of a managed configuration mutation during the spike.
Architecture: existing PostgreSQL wire ingress and bounded scheduler, backed by an owned PgBouncer process using verified TLS to provider PostgreSQL (Supabase session endpoint when direct IPv6 is unavailable). Reserve connections are warmed before ingress readiness. A local50ms controller releases already-approved reserve on waiting demand and reduces admission on pressure. Provider settings stay unchanged during traffic. Provider pressure retains source timestamps, plus direct SQL health/inventory checked each second. No SQL replay, no active transaction termination, no claim to beat an equally sized warm fixed pool.
Constraints: all3 providers mandatory, AI/priority deferred; preserve dirty work; private loopback listener and private files; explicit exclusive single-owner budget; stale/unknown observations stop new admission; uncertainty cannot release slots or grow; active transactions retain permits. Existing native managed-resize adapter retained. No production/HA claim.
Alternatives considered: faster management PATCH cannot bypass provider propagation or Supavisor termination; an application SDK restricts languages. Chosen native endpoint reuses mature PgBouncer and existing tested protocol admission.
