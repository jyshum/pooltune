# Pooltune database problems and niches

**Pooltune needs a customer problem before it needs a larger feature list.** Several different problems make an app feel slow, and they do not all need a database change. The useful starting point is to understand which job a developer repeatedly struggles to finish, then check what Supabase exposes and what the owner would let an agent change unattended. Four directions deserve comparison: slow interactions as data changes, performance regressions after releases, recurring cleanup problems, and background jobs interfering with customer requests. The research supports their technical plausibility, but does not establish a market winner. The earlier optimization catalog remains a possible toolbox, not eight required product pillars.

Prepared November 12, 2026. This is product research and brainstorming, not a build plan. No live project was inspected, no changes were made, and no implementation or publication is approved. Hosted Supabase remains the starting environment. The current boundaries remain no additional traffic proxy, no killing customer transactions, and no automatic spending.

## Start with the work, not the database setting

A database stores information and answers requests about it. A request might mean “show this customer's latest 20 orders,” “update this payment,” or “total every sale this year.” A **bottleneck** is the part limiting how quickly that work finishes. The request could be doing unnecessary work, waiting behind other work, or using all available resources. The visible symptom can be identical: a page takes too long.

Three changes matter separately. **More data** makes searching or sorting harder even with the same number of users. **More simultaneous users** makes otherwise reasonable requests compete. **Harder questions** introduce work such as searching text, checking permissions, or comparing long histories. A fourth possibility sits outside database execution: the app sends many separate requests, transfers unnecessary data, or waits on a distant service.

For example, one slow search occupies a database connection longer. Other requests then queue for connections. Increasing the connection allowance treats the queue but could let more expensive searches compete and make the original problem worse. Supabase already distinguishes resource and waiting signals; those signals guide investigation rather than prove a cause. ([Supabase reports](https://supabase.com/docs/guides/observability/reports), [PostgreSQL activity and waits](https://www.postgresql.org/docs/17/monitoring-stats.html))

The following stories are illustrative mechanisms, not claimed incidents in Jared's projects or estimates of market frequency.

### Eight problems hide behind “my app is slow”

| Customer-visible problem | Why it happens and what already helps | Context still needed and a meaningful outcome |
|---|---|---|
| **A familiar screen slows as records accumulate.** An orders list returns 20 rows but examines thousands first. | An **index**, a maintained lookup structure, can reduce searching. PostgreSQL already chooses among available indexes and other approaches. An absent or unsuitable lookup structure can still leave excess work. | Preserve the same sorting, results, and permissions. Success is a faster interaction with less unnecessary work and acceptable write cost, not simply “an index was created.” |
| **One customer or filter is unusually slow.** Most accounts look fine; a large tenant times out. | The **planner**, PostgreSQL's method chooser, uses sampled statistics to estimate work. Uneven data or relationships between columns can defeat average estimates or a reused plan. | Identify representative inputs and actual user permissions. Success is helping the affected case without making common cases worse. Tenant identity cannot safely be guessed from a column name. |
| **The database is fast but the page is slow.** A screen performs many sequential calls or downloads fields it never uses. | PostgreSQL handles each request it receives. Application batching and narrower responses can help, but the database cannot automatically combine requests the app has not sent yet. | The page timeline and code matter. Success means fewer trips or transferred bytes and faster completion, rather than shaving a millisecond from an already-fast query. |
| **Updates hang or jobs interfere.** One operation holds something another needs, or several jobs run together. | A **transaction** groups changes into one unit; a **lock** protects conflicting work until the relevant transaction finishes. Pools reuse connections, and PostgreSQL detects deadlocks, but neither determines business priorities. | Know who owns the blocking work and which jobs can move. Success means future work completes with less waiting while required jobs still meet deadlines. Current blockers cannot always be released under the no-interruption boundary. |
| **Searches or reports need too much scratch space.** Sorting or combining results spills from memory to disk. | PostgreSQL limits working memory so concurrent tasks cannot each consume everything. A **spill** is temporary storage used when an operation exceeds that allowance. Existing indexes and better plans can sometimes avoid the work. | Decide whether all requested work is necessary and whether memory is available across all callers. Success is lower waiting and temporary work at the same useful workload, without memory failures elsewhere. |
| **A frequently changed table grows or slows despite cleanup.** Imports, queues, or session data create repeated updates and deletions. | PostgreSQL retains old versions while they might still be needed. **Autovacuum** automatically cleans eligible versions and refreshes planning information. Cleanup can run late, lack resources, or be unable to remove versions still needed by old transactions. | Distinguish late cleanup from blocked cleanup and reusable space. Success is sustainable maintenance and stable useful performance, not necessarily a smaller disk file immediately. |
| **Legitimate work reaches a real resource limit.** Useful writes, reports, or storage growth exceed the machine's capacity. | Managed services supply finite processing, memory, disk speed and space. Some workloads can be made cheaper; others genuinely require more resources. | Know retention, deadlines and spending choices. Success can be a well-supported capacity recommendation rather than pretending every upgrade is avoidable. |
| **The provider or network is failing.** Requests are slow or rejected while database execution looks normal. | Regional routing, gateways, authentication services and managed rollouts are provider responsibilities. Local query changes do not repair a provider network defect. | Identify the affected layer and preserve evidence. Success is accurate escalation and avoiding distracting database changes while the provider resolves its incident. |

The mechanisms have direct documentation support: indexes add write cost as well as helping reads; statistics are approximations; app patterns can produce repeated calls; temporary work consumes resources; automatic cleanup has visibility constraints. ([Indexes](https://www.postgresql.org/docs/17/indexes-intro.html), [Planner statistics](https://www.postgresql.org/docs/17/planner-stats.html), [Repeated-query examples](https://www.prisma.io/docs/orm/v7/prisma-client/queries/advanced/query-optimization-performance), [Memory limits](https://www.postgresql.org/docs/17/runtime-config-resource.html), [Routine cleanup](https://www.postgresql.org/docs/17/routine-vacuuming.html))

Some difficult cases also involve application meaning. Search ranking, complete financial exports, allowed tenant access, and “all time” reporting cannot silently become cheaper but different answers. **RLS**, row-level security, controls which records a user can access; testing as a privileged database owner can hide both its cost and its behavior. Supabase documents this exact performance distinction. ([RLS performance](https://supabase.com/docs/guides/database/postgres/row-level-security-performance))

Public cases show that these distinctions matter without establishing prevalence. One developer reported that an index helped, but the largest improvement came from combining sequential requests into one database function. Another user associated instability with a frequent background job but explicitly did not establish the scheduling change as the sole cause. These are first-person accounts, not reproduced experiments. Separately, Supabase's February 2026 incident report documents a regional network problem resolved through provider action. ([Developer account](https://www.reddit.com/r/SaaS/comments/1qqacnk/using_supabase_slow_query_reports_llms_to_fix/), [Background-job discussion](https://github.com/orgs/supabase/discussions/51210), [Official provider incident](https://supabase.com/blog/supabase-incident-on-february-12-2026))

## Supabase already helps; the possible gap is finishing the right repair

Supabase tunes PostgreSQL to the selected compute size. Its documentation explicitly says those defaults assume a general workflow and particular workloads can benefit from further tuning. Supavisor and PostgREST already grow their connection pools with demand within configured limits. PostgreSQL already analyzes data and cleans up automatically. The starting claim should therefore not be “managed databases do not optimize themselves.” ([Supabase tuning](https://supabase.com/docs/guides/platform/performance), [Supavisor FAQ](https://supabase.com/kb/troubleshooting/supavisor-faq-YyP5tI), [PostgREST pools](https://docs.postgrest.org/en/latest/references/connection_pool.html))

Supabase also provides advisors, query inspection, and an hourly read-only performance-agent workflow. That workflow checks changes in measurements, blockers, and advisor findings; it can also run after schema changes. It does not create indexes, rewrite queries, or cancel sessions. A generic report or recurring “something looks slow” message would overlap heavily with these existing tools. ([Advisors](https://supabase.com/docs/guides/observability/advisors), [Existing performance agent](https://supabase.com/docs/guides/observability/automate-with-agents/performance))

The **product hypothesis** is that a developer still needs help connecting a symptom to the right cause, completing an allowed repair, and checking that it worked. The missing context can be the affected feature, tenant, recent release, background-job deadline, or authorization rule. Sometimes a bounded database change finishes the job. Sometimes the useful deliverable is a tested application/query migration. Sometimes the correct result is “this is a provider issue” or “no change is warranted.”

That gap is not yet proven to justify an always-running product. A coding assistant with a slow-query export might already finish an occasional problem. A native default might recover without intervention. A single durable setting might remove the recurring issue. Pooltune should measure the remaining human work instead of treating tool availability as evidence of demand.

## Check real access only after identifying the problem

Supabase supplies an **API**, a remote interface for reading or changing supported service information, and an **SDK**, a programming library used by applications. PostgreSQL supplies SQL, the database's command language. There is no single SDK operation called “optimize this app.” These interfaces expose different evidence and authority.

The table below describes documented feasibility. It does not mean an integration has been tested on Jared's projects or that every account exposes every signal.

| Product question or job | Actual surface | What it can support, and what remains missing |
|---|---|---|
| Is useful work slowed by resource or connection pressure? | Management metrics and provider logs | Observe resource trends, waiting and failures. They do not by themselves identify the responsible screen or prove its full response time. |
| Which database requests consume work? | SQL query statistics and activity views, available through authorized diagnostic access | Compare repeated query patterns, current waits and maintenance history. Aggregated averages are not a distribution of page load times or a complete failure history. |
| Why does a known request do so much work? | PostgreSQL query plans; optional Supabase client `.explain()` | Inspect the method chosen for a query. Client plan access is disabled by default; execution-based analysis actually runs the query and needs controlled use. |
| Is the page slow outside the database? | Application tracing, with supported Supabase SDK trace propagation | Connect application timing with gateway/function evidence where supported. It requires application instrumentation; provider credentials do not automatically supply it. |
| Can a bounded database repair happen unattended? | Authorized SQL maintenance connection; some Management configuration APIs | Eligible indexes, planner-information repairs, or maintenance can be possible after a standing grant. Read permission does not imply table ownership or maintenance authority. |
| Can background work move safely? | Supabase Cron schedules/history and its job-management function | Change an enrolled job's future schedule under job-owner authority. The owner must supply flexibility/deadlines; SQL alone does not reveal business importance. |
| Can the application ask a better question? | SDK features plus repository or migration/deployment access | Prepare and test batching, narrower reads, query or policy changes. Management access does not edit deployed app code or establish equivalent behavior. |
| Can a provider defect be fixed locally? | Status/incident evidence and support escalation | Identify likely external failure. No customer SQL permission grants control over provider routing or fleet repairs. |

These surfaces are documented in the [metrics API](https://supabase.com/docs/reference/api/v1-scrape-project-metrics), [read-only SQL endpoint](https://supabase.com/docs/reference/api/v1-read-only-query), [query-plan guide](https://supabase.com/docs/guides/api/query-plans), [client tracing](https://supabase.com/docs/guides/observability/client-side-tracing), [Cron guide](https://supabase.com/docs/guides/cron), and [SDK selection/nested reads](https://supabase.com/docs/reference/javascript/select).

The practical autonomy distinction is between **bounded database changes with known effects**, **application/security changes requiring additional context and a deployment path**, and **problems owned by the provider**. A standing permission could allow the first category without prompting for every operation. The second is not automatically impossible, but requires more product integration and correctness evidence. AI-generated code is not proof that permissions, billing behavior, retries, or returned results are preserved.

Maintenance also has a different access path from ordinary app requests. Some operations cannot run inside an application function's transaction. PostgreSQL versions differ in maintenance grants; creating indexes needs stronger authority than read-only inspection. The product must discover capability and explain unsupported actions rather than ask for one broad credential and assume everything works. ([VACUUM requirements](https://www.postgresql.org/docs/17/sql-vacuum.html), [Connection options](https://supabase.com/docs/guides/database/connecting-to-postgres))

Without app traces, the honest promise concerns provider-visible requests and database work. A request can finish at the server after the user already gave up. One-minute resource samples also cannot promise rescue of a request currently timing out. These limits affect which customer outcome Pooltune should offer.

### Compact interface reference

| Purpose | Documented interface |
|---|---|
| Metrics | `GET /v1/projects/{ref}/analytics/endpoints/metrics` |
| Logs | `GET /v1/projects/{ref}/analytics/endpoints/logs` |
| Read-only SQL | `POST /v1/projects/{ref}/database/query/read-only` |
| Supavisor ceiling | `PATCH /v1/projects/{ref}/config/database/pooler` |
| PostgREST configuration | `PATCH /v1/projects/{ref}/postgrest` |

Analytics scopes cover the first two endpoints; database-read scope covers the read-only endpoint. Mutation scopes and SQL privileges are separate. Project/plan availability, actual field access, configuration propagation and restoration still need testing. ([Metrics reference](https://supabase.com/docs/reference/api/v1-scrape-project-metrics), [Log reference](https://supabase.com/docs/reference/api/v1-get-project-logs), [Read-only reference](https://supabase.com/docs/reference/api/v1-read-only-query), [Pooler update](https://supabase.com/docs/reference/api/v1-update-pooler-config), [PostgREST update](https://supabase.com/docs/reference/api/v1-update-postgrest-service-config))

## Compare four products rather than choose from available knobs

All four niches below are hypotheses. Native tools overlap with each, and none has demonstrated recurring demand or successful unattended intervention yet.

| Niche | Person, trigger, and job | Proposed outcome and native overlap | Autonomy fit and biggest uncertainty |
|---|---|---|---|
| **Slow interactions as data changes** | App developer sees a search, list or dashboard degrade as records or customer distributions change. Find the delay and finish a repair. | The actual interaction becomes faster with unchanged results/access. Advisors already identify some database issues; coding assistants can handle on-demand fixes. | Some database changes fit standing grants, but valuable fixes may be app code. Is the recurring pain database repair, app redesign, or attribution? |
| **Performance regression after a release** | Developer/team deploys code, schema or permission changes and needs to know whether important operations worsened. | Detect and explain a regression, then deliver a verified fix. Native checks and CI, automated release tests, can already catch part of this. | A release provides a useful trigger and test opportunity. Often better release-triggered than always-on. Can comparable baselines and deployment context be obtained? |
| **Write and cleanup maintenance** | Owner of import, event, queue or sync workloads repeatedly sees cleanup/planning fall behind as data changes. | Keep useful operations and cleanup healthy across cycles. Native autovacuum is already the baseline. | Stronger fit for standing table grants and bounded maintenance. Does intervention recur, or do native maintenance/one setting solve the job permanently? |
| **Scheduled-work interference** | Developer owns background jobs and customer-facing requests that slow during repeated busy windows. | Jobs still finish on time while foreground requests suffer less. Cron already schedules jobs and serializes each job's own repeated runs. | Standing schedule windows can support unattended changes. Are jobs genuinely deferrable, and does static staggering eliminate the need for ongoing optimization? |

An **outlier-customer variant** could narrow the first niche: “one large customer's dashboard is slow while averages look normal.” That creates a concrete investigation target but needs tenant attribution and representative inputs. It does not authorize giving one customer priority or weakening another customer's access.

The first niche has the broadest immediate human appeal, but it risks becoming a general app-performance assistant. The second has a clearer trigger, yet its most natural form could be a release check rather than continuous monitoring. Maintenance and approved job scheduling are **technically more compatible with unattended operation** because their targets and permitted changes can be bounded. That is an engineering inference, not evidence that those markets are larger or that Jared should choose either now.

Capacity and cost are adjacent outcomes across these niches. Removing unnecessary work might avoid a later upgrade, but lower estimated query cost is not a verified bill saving. A true capacity limit can be the right answer. This does not need to return the product to a traffic-spike pitch or imply automatic purchases.

## Choose the product contract from real episodes

The next decisions are about the product, not its framework or services. Pick a **target user**, a **trigger**, an **outcome**, a **permission envelope**, and an **exception experience**. For example, “owner of an import-heavy app; after repeated imports; sustain expected request performance; maintenance on selected tables; ask only when the cause requires app changes or forbidden interruption” is a testable product hypothesis. It is not a selected niche.

Unattended operation after choosing settings remains compatible with this approach. The owner chooses what the product may change and the limits that matter. Pooltune should remain quiet when healthy, show completed verified work, and surface a specific exception when the evidence is missing or the necessary action exceeds the grant. A full stop must prevent new actions; it cannot promise instant reversal of already running work or completed maintenance.

### A short discovery pass can eliminate weak directions

Start by reconstructing a few real episodes from Jared's own projects and, if useful, willing users: what became slow, when, who noticed, how it was investigated, what fixed it, and what remained uncertain. Compare the existing Supabase advisor/read-only agent and coding-assistant workflow before assuming a gap. This asks what people actually did, rather than whether they like an “AI database agent.”

If separately authorized, observe representative project activity read-only and connect relevant release/job events. Record useful opportunities, native-tool coverage, missing context, and cases outside the database. Then replay specific cases in controlled test data to ask whether a bounded repair can finish the job correctly. Personal projects establish realism and feasibility, not market prevalence; synthetic workloads establish mechanics, not customer frequency.

Compare **on-demand assistance**, **release-triggered checks**, and **ongoing unattended care** by human effort saved and completion quality. Do not assume ongoing operation is superior because an agent can run continuously. Count eligible useful repairs, avoided unnecessary changes, verification effort, recurrence, and willingness to grant standing permission.

Use explicit reasons to stop or narrow a direction. If native tooling already finishes the job, the gap is weak. If most delay is app/network behavior, a database-only promise is wrong. If a one-off change removes the problem, recurring automation needs another justification. If owners will not grant necessary permissions, a reviewed workflow is a different product worth evaluating honestly. If no relevant event appears during a short window, record insufficient evidence and inspect history or extend observation rather than claim no demand.

### Free use and API credits

An open-source Pooltune can be freely usable without a software license fee, while users run it themselves and bring their own model access. That still leaves model calls, hosting, and applicable provider-observability costs. Using Jared's own credits could fund a prototype; it would not establish that a hosted service remains free indefinitely.

If the displayed Claude balance is eligible **Claude API credit in the Claude Console**, it can pay for API usage. Anthropic documents prepaid credits for that purpose. We have not verified the balance type, amount, expiry, or restrictions, so we cannot infer how long it will last or treat a subscription benefit as interchangeable API credit. ([Anthropic API billing](https://support.claude.com/en/articles/8977456-how-do-i-pay-for-my-claude-api-usage))

The most useful next question is concrete: **Which of your Supabase projects last had a slow user action, a release regression, an import/cleanup problem, or background-job interference, and what did you have to do manually?** A second question follows from that episode: **would the valuable result have been an unattended database repair, a tested app/query change, or simply establishing which layer was responsible?** Those answers can narrow the product before committing to a niche or all the possible capabilities.
