# Prove repairs across changing query workloads

**The index incident is a credible example of a repair Pooltune could discover, perform, and measure using documented Supabase/PostgreSQL capabilities. It is not a repair we have reproduced.** It represents a broad class of inefficient lookups, not one special query. The same product can address poor planner information, selected temporary-disk problems, and particular cleanup failures. Those causes need different evidence and experiments. The recommended starting point is one complete diagnosis-to-verification workflow for indexes and statistics, then separately qualify maintenance and scoped function repairs. Keep the investigation broad enough to recognize competing causes while limiting automatic changes to demonstrated repair contracts.

Prepared November 12, 2026. Research and product brainstorming only. No Supabase project was inspected, cloned, or changed; no Pooltune evaluation has run.

## The index account supports a mechanism, not a guaranteed speedup

The published quota-check query filters by `metric_name` and `state`, orders by `breach_detected_at`, and requests one result. Its existing index contains `(metric_name, breach_detected_at)`. The replacement **adds the missing `state` column** between those columns. This is not merely rearranging the same index keys. The account shows an execution taking **605.274 ms with 232,178 shared blocks read**, followed by one taking **0.048 ms with three shared buffer hits**. Both return zero rows. PostgreSQL documents why equality filters followed by ordered access can benefit from a matching multicolumn index. ([Firsthand account](https://adityajindal.dev/writing/postgres-index-win), [Multicolumn indexes](https://www.postgresql.org/docs/17/indexes-multicolumn.html))

Those plans support a substantial reduction in database work. They do not establish a controlled latency multiplier: the before run reads blocks while the after run finds them in cache. The article does not supply the complete dataset, role/parameter mix, concurrent workload, or write-cost measurements. It describes PostgreSQL on RDS, not a verified Supabase reproduction. The reported improvement to another page is useful context, but cannot be independently reconstructed from the supplied evidence. A Pooltune fixture can demonstrate this **class of repair** without pretending to reproduce that company's exact outcome.

The other three startup examples remain useful. Chatbase supplies partial-repair cases involving reporting interference; incident.io supplies an application-transaction cause that a pool adjustment would miss; Lago supplies a workload-separation boundary. They should test whether the agent recognizes limits rather than become promises to automate replicas, application changes, or a ClickHouse migration. ([Chatbase](https://supabase.com/customers/chatbase), [incident.io](https://incident.io/blog/database-performance), [Lago](https://github.com/getlago/lago/wiki/Using-Clickhouse-to-scale-an-events-engine))

## Monitoring finds expensive patterns before choosing a repair

Supabase exposes PostgreSQL statement statistics through `pg_stat_statements`. These group structurally similar queries and record executions, elapsed execution time, returned or affected rows, database-page activity, temporary-disk activity, and other counters. Periodic snapshots can show that a recurring query became slower or contributes substantial work. A moderately expensive query executed constantly can matter more than a rare slow report. ([Supabase query statistics](https://supabase.com/docs/guides/database/extensions/pg_stat_statements), [PostgreSQL fields](https://www.postgresql.org/docs/17/pgstatstatements.html))

For valid intervals, average execution duration is the increase in `total_exec_time` divided by the increase in `calls`. Similar per-call comparisons apply to buffer and temporary-block counters. Resets, evicted entries, collection gaps, and version differences must be handled. **Execution time is not CPU time; `rows` is not rows examined; averages are not p95.** Failed requests also need error evidence. Nested function statements can be hidden by default tracking, while counting nested and outer statements together can double-count workload contribution. ([Statement statistics](https://www.postgresql.org/docs/17/pgstatstatements.html))

The first finding should therefore read: “This repeated query became slower and reads many database pages per execution.” It should not jump to “create this index.” Query plans provide the next evidence: how PostgreSQL searches, filters, joins, and sorts. An estimated plan predicts work; `EXPLAIN ANALYZE` actually executes the statement and reports observed behavior. A sequential scan is sometimes correct, especially for small tables or requests needing most rows. ([Reading query plans](https://www.postgresql.org/docs/17/using-explain.html))

Discovery is possible without application instrumentation, but verification needs representative values and roles. Normalized SQL usually replaces values with placeholders. It is not a complete request recording. Testing as an administrator can bypass customer access rules and produce an unrepresentative plan. Database measurements support database-performance claims; proving a page became faster requires application measurements. ([Statement normalization](https://www.postgresql.org/docs/17/pgstatstatements.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Client tracing](https://supabase.com/docs/guides/observability/client-side-tracing))

The documented read-only Management API provides an inspection route, but its identity and permissions must be checked against the required views. It does not grant index creation authority. Supported documentation establishes available ingredients, not successful access in a particular project. ([Read-only query API](https://supabase.com/docs/reference/api/v1-read-only-query))

## Test a few plausible repairs under representative conditions

For the index case, the agent would inspect the query's filters, ordering, existing indexes, and measured plan, then propose a small number of matching index candidates. It keeps the query's meaning unchanged. **Thousands of arbitrary rewritten queries are unnecessary.** Supabase's native Index Advisor is useful input but currently documents single-column B-tree recommendations; it does not supply the exact compound candidate needed here. Pooltune needs its own bounded candidate reasoning. ([Index Advisor](https://supabase.com/docs/guides/database/extensions/index_advisor))

HypoPG can cheaply ask whether PostgreSQL would choose a hypothetical index before building it. This is a planning experiment in the same database session, not a measured speedup: hypothetical indexes do not work with `EXPLAIN ANALYZE`. Promising candidates then need actual indexes and repeated execution against suitable test data. ([Supabase HypoPG](https://supabase.com/docs/guides/database/extensions/hypopg), [HypoPG limitations](https://github.com/HypoPG/hypopg))

A useful experiment includes common, rare, and no-result searches; small and large customers; relevant access roles; realistic simultaneous reads and writes; and comparable cache conditions. Application prepared-query behavior also matters because a shared generic plan can differ from a plan selected for one literal value. Measure duration and database work, preserve returned results, and check writes, errors, storage, and neighboring important queries. ([Prepared plans](https://www.postgresql.org/docs/17/sql-prepare.html), [Index costs](https://www.postgresql.org/docs/17/indexes-intro.html))

A clone is an option, not automatic proof. Supabase branches are data-less by default, while current Dashboard documentation offers **Include data with Point-in-Time Recovery**, with associated resources and costs. Programmatic access to that particular data-copy option was not verified here. Existing representative staging or carefully seeded fixtures can also help. A copy does not recreate live concurrency or request sequences. Physical restores can start copied scheduled jobs or external activity, so experiment isolation must account for that documented behavior. ([Branching](https://supabase.com/docs/guides/deployment/branching), [Include data](https://supabase.com/docs/guides/deployment/branching/dashboard), [Restore behavior](https://supabase.com/docs/guides/platform/clone-project))

After qualification, one authorized concurrent index build can avoid blocking ordinary writes, but still consumes resources, can wait, and can leave an invalid object after failure. It requires suitable ownership/schema rights and execution outside a transaction block. A valid index affects the broader workload; there is no ordinary one-percent-user index rollout. Production verification must compare relevant workload windows and support removing only the eligible Pooltune-created object when needed. That removal cannot undo resources already spent building it. ([CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html))

## Eight families cover different measurable causes

This matrix describes proposed eligibility, not already-proven autonomous features. The shared customer problem is an important query workload becoming expensive; each row is a different possible cause.

| Family and concrete problem | Evidence beyond “slow” | Eligible action | What would establish benefit |
|---|---|---|---|
| **Indexes:** repeated filtering or ordering searches unnecessary data | Representative plan, matching predicates, existing-index comparison, high access work | Add one tested nonunique index | Faster representative reads with less work; acceptable writes, storage, and neighboring queries |
| **Statistics:** an import or skewed customer causes poor execution choices | Incorrect estimated versus actual rows, analysis history, parameter variation | Targeted ANALYZE; qualified extended statistics or column-detail increase | Better execution across relevant inputs, not merely better estimates |
| **Maintenance:** an index-only query still visits many table pages, or cleanup repeatedly falls behind | Heap fetches, churn, cleanup history; exclude old transactions pinning rows | Bounded VACUUM or justified table-specific maintenance policy | Reduced unnecessary access or sustainable cleanup, without unacceptable maintenance interference |
| **Scoped function execution:** necessary internal sort/hash work spills to disk | Temporary blocks plus an actual internal plan; bounded concurrent callers | Small memory adjustment for an eligible enrolled database function | Less temporary work and lower duration under concurrent load, with acceptable memory use |
| **Pool control:** requests genuinely wait at the configured connection ceiling | Acquisition waits/failures, correct ceiling reached, database headroom; exclude slow work and blockers | Bounded ceiling adjustment | Fewer acquisition failures without reduced completed work or resource overload |
| **Scheduled work:** separate jobs repeatedly overlap with foreground degradation | Job timing, query/wait/resource correlation, permitted scheduling windows | Shift future job schedules | Jobs still meet deadlines and foreground requests improve across repeated windows |
| **WAL/checkpoints:** write flushing demonstrably causes unnecessary pressure | Checkpoint frequency/reasons, write-log volume, disk evidence | Qualified checkpoint-budget change | Better write/query behavior across cycles within storage and recovery budgets |
| **Reviewed code/policy:** repeated query or authorization work requires a logic change | Real-role plans, source context, expected result/access behavior | Prepare and test a narrow migration or code patch | Same intended results and permissions, better performance; separate deployment authority |

Statistics mechanisms are documented, including limits on extended statistics. Maintenance already happens automatically in PostgreSQL, and a large dead-row count alone does not prove intervention helps. Function memory multiplies across operations and callers. These constraints are why each row needs a specific contract. ([Planner statistics](https://www.postgresql.org/docs/17/planner-stats.html), [Maintenance](https://www.postgresql.org/docs/17/routine-vacuuming.html), [Memory](https://www.postgresql.org/docs/17/runtime-config-resource.html), [Function settings](https://www.postgresql.org/docs/17/sql-createfunction.html))

The remaining interfaces are real but conditional: Supavisor grows connections within its ceiling; Cron exposes scheduling and run history; Supabase exposes selected PostgreSQL configuration settings; policy optimization requires access-preserving tests. Current blockage has no universal unattended repair, and terminating customer transactions remains outside scope. ([Supavisor](https://supabase.com/kb/troubleshooting/supavisor-faq-YyP5tI), [Cron](https://supabase.com/docs/guides/cron), [Configuration API](https://supabase.com/docs/reference/api/v1-update-postgres-config), [RLS performance](https://supabase.com/docs/guides/database/postgres/row-level-security-performance))

## Conclusion

**The index class is broad enough for the first complete working slice; one scripted index demonstration is not enough for release confidence.** Begin evaluations with symptoms and imperfect evidence, hiding the expected cause. Include missing compound indexes, stale statistics, skew, already-correct indexes, healthy full scans, blocking, insufficient permissions, failed builds, and repeat runs. Score actual useful repairs, unnecessary changes, false success claims, and recovery. This evaluates the model and harness together rather than whether SQL commands execute. ([Agent evaluation guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents))

A useful expanded V1 can qualify index and statistics repairs first, then narrow maintenance and function-memory cases. Pool, scheduling, checkpoint, and reviewed-patch work remain conditional catalog capabilities. Breadth should grow when additional families complete meaningful cases without unacceptable regressions. This is a testable scope recommendation, not an approved implementation plan or a claim that the agent already performs reliably.
