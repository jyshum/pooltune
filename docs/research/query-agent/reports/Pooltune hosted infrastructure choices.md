# Pooltune keeps customer databases in place

Research recommendation, November 12, 2026. Fully hosted deployment and the six repair types are accepted product decisions. The implementation below is proposed, not built, tested, or approved.

**Pooltune does not need a copy of each customer's database.** Its workers retrieve current performance evidence from the customer's Supabase project and execute permitted repairs there. Pooltune's own database holds accounts, permissions, measurements, investigation history, and job progress. That distinction makes a simple hosted service possible without turning Pooltune into another database hosting provider. I recommend Go for the API and workers, the existing React/TypeScript dashboard, managed PostgreSQL for operational state, and Anthropic's official Go SDK. Reliability comes primarily from fresh evidence, bounded execution, durable records, and verified outcomes, rather than a particular implementation language.

## Live evidence comes from the customer database

The customer's Supabase remains the source of truth for their application records, current schema, indexes, execution statistics, and active database conditions. A Pooltune worker connects to that project when it needs fresh evidence. Our database answers different questions: what was observed yesterday, which actions are permitted, whether another worker already started a repair, and what happened afterward. **Retrieval therefore has two sources: live database facts from the customer, operational memory from Pooltune.** Historical measurements help identify regressions but cannot substitute for checking current state before a change.

For example, a worker reads query statistics from customer Supabase, notices a query is taking longer, and compares that observation with our stored baseline. It then retrieves the relevant schema and query plan from the customer database. If an index is justified and authorized, the worker creates it in that same customer database and retrieves fresh measurements afterward. Our database saves the investigation and outcome. It does not need to save the invoices, messages, or customer records that the query accesses. PostgreSQL provides execution counters and page-access statistics through `pg_stat_statements`; Supabase supports backend PostgreSQL connections for this interaction. ([PostgreSQL query statistics](https://www.postgresql.org/docs/17/pgstatstatements.html), [Supabase connections](https://supabase.com/docs/guides/database/connecting-to-postgres))

Routine collection should ingest bounded numeric measurements, timestamps, reset markers, and query identities. On-demand investigations can retrieve relevant schema definitions, sanitized SQL structure, plans, and experiment results. Our persistent records also include tenant/project ownership, grants, queued work, action state, and model usage. Credentials belong in protected secret storage or encrypted records with separately controlled keys. Entire application tables, full request bodies, unrestricted logs, and database replicas should be outside default collection.

This boundary is meaningful, but it is not a promise that no sensitive information leaves Supabase. SQL text and plans can contain literal values; PostgreSQL explicitly warns that normalized query text can sometimes retain constants. Selected diagnostic evidence reaches our servers, and evidence included in model requests reaches Anthropic. Redaction must cover prompts, logs, traces, and stored artifacts. Also, aggregate statistics do not provide every representative query parameter or user role needed for testing. Missing context must make a repair ineligible until suitable evidence is authorized and available. ([Query normalization limitations](https://www.postgresql.org/docs/17/pgstatstatements.html), [Execution-plan contents](https://www.postgresql.org/docs/17/using-explain.html))

The browser only displays and configures the service. Collection cannot depend on it because monitoring must continue when it closes. Database work can remain in customer Supabase while selected outputs travel to our backend. That is the relevant boundary, rather than calling all processing “client-side.”

## Go offers the simplest supported starting point

Go is the strongest recommendation because the existing repository already contains Go database integration and a bounded agent tool loop. Reusing suitable pieces avoids introducing a new backend language before the new repair workflow is proven. Anthropic provides an official Go SDK, alongside TypeScript, Python, Java, and others. Rust and C++ can call the HTTP API, but neither appears in the reviewed official SDK list. An SDK handles API interaction; it does not supply Pooltune's complete investigation, permissions, or recovery system. ([Anthropic SDKs](https://platform.claude.com/docs/en/cli-sdks-libraries/overview))

Rust remains a legitimate choice if learning it or controlling runtime behavior is an explicit project goal. It requires additional integration work relative to the existing Go code and official client. C++ has no demonstrated advantage for this workload: no locally intensive numerical or systems algorithm currently justifies selecting it. Most work involves waiting for PostgreSQL, external APIs, or model responses. Python can support production services, and this research found no benchmark showing its memory use would dominate Pooltune's costs. User preference and existing Go investment are enough to choose differently without inventing a performance problem.

TypeScript is the strongest alternative if LangGraph's persisted workflow model materially simplifies implementation. LangGraph can save investigation checkpoints and resume work. A durable queue would still schedule jobs, and application code would still enforce permission and repair rules. Neither checkpoints nor a graph framework make external SQL effects safe to repeat automatically. Start with one backend language; splitting Go collection from TypeScript reasoning adds deployment and coordination work before its benefit is established. ([LangGraph persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence))

The proposed deployment has a web/API service, a separate background worker service, managed PostgreSQL, and managed secret storage. The dashboard can remain React/TypeScript. PostgreSQL stores ordinary relational records and bounded JSONB evidence, so varied customer schemas do not require MongoDB. River is a practical Go queue candidate because it stores work in PostgreSQL, although some advanced features are paid and must be checked before selection. ([PostgreSQL JSONB](https://www.postgresql.org/docs/17/datatype-json.html), [River features](https://riverqueue.com/docs))

Railway persistent services are a reasonable pilot host; worker sleeping should be disabled. Cloud Run services plus worker pools are an alternative, with worker-pool scaling requiring explicit configuration. For River's own database connection, use a supported direct or session-pooled mode because runtime services use session features. Customer inspection and repair connections need their own operation-specific configuration. These are researched candidates, not deployed integrations. ([Railway service types](https://docs.railway.com/services), [Cloud Run resource types](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run), [River pooling](https://riverqueue.com/docs/pgbouncer))

## Shared workers need limits and durable recovery

**Each customer does not need a dedicated server, process, or continuously running model.** Shared workers pick up jobs carrying verified tenant and project identity. Lightweight collection, model investigations, and expensive experiments should have separate concurrency budgets. This prevents a long repair from blocking routine monitoring. Initial proposals include one active modifying repair per project, small customer connection budgets, global investigation limits, and staggered collection schedules. Exact limits require measurement.

Model requests need both customer and global budgets. Anthropic imposes organization-level limits on spending, requests, and tokens, so adding workers cannot create unlimited model capacity. Before making calls, reserve bounded usage, enforce maximum turns/output, and account for actual consumption afterward. A noisy customer should not exhaust every other customer's capacity. Keep the Anthropic key on our servers. ([Anthropic rate limits](https://platform.claude.com/docs/en/api/rate-limits))

Durable records preserve progress when containers restart. Queue jobs can nevertheless run more than once after uncertain completion. Suppose an index finishes building but the worker loses its connection before recording success. Retrying blindly could create conflicting work. The recovery path must inspect the customer's actual index definition, validity, and operation progress before proceeding. Queue uniqueness alone does not solve this. PostgreSQL concurrent index creation can leave invalid indexes after failure and cannot run inside a transaction block. ([River execution guarantees](https://riverqueue.com/docs/reliable-workers), [PostgreSQL index creation](https://www.postgresql.org/docs/17/sql-createindex.html))

Worker leases coordinate ownership, but an expired lease does not stop SQL already running in customer Supabase. Uncertain operations need reconciliation before conflicting repairs resume. If Pooltune cannot read authoritative permissions and action state, it should stop admitting new changes. Ordinary customer application traffic continues using its existing database path; Pooltune is not its traffic proxy. Already-submitted maintenance can still continue and must be accounted for after recovery.

Tenant isolation also needs explicit backend checks. Signing into Pooltune, authorizing Supabase Management API access, and granting SQL repair privileges are separate steps. A successful Connect flow does not prove all six repairs are available. Supabase's OAuth guide says an existing database password cannot be retrieved through the Management API. The exact narrow SQL role and onboarding flow remain an implementation experiment, not a solved detail. ([Supabase OAuth integration](https://supabase.com/docs/guides/integrations/build-a-supabase-oauth-integration))

## Agent quality depends on trustworthy execution

The model can propose a plausible diagnosis, but infrastructure determines whether its evidence is fresh, its tools are authorized, its progress survives, and its result is measured correctly. Tool contracts and ordinary code must enforce those requirements independently of model confidence. Database counters are cumulative, can reset, and can disappear from tracking; measurement code must handle those cases. Query execution time is not per-query CPU, and averages are not application latency percentiles. Supabase resource metrics add useful context but their documented beta interface requires capability and version checks. ([PostgreSQL counters](https://www.postgresql.org/docs/17/pgstatstatements.html), [Supabase metrics](https://supabase.com/docs/guides/observability/metrics))

The service scales with connected projects, tracked query patterns, sample frequency, retained history, and concurrent investigations. Customer row counts affect source-side investigation costs without requiring those rows to be copied. Store query text once where practical, cap evidence sizes, expire detailed samples, and aggregate older measurements. Add workers when queue delays rise and downstream databases and model quotas have spare capacity. More workers can worsen an already saturated dependency.

No customer capacity, runtime speed ranking, or savings estimate has been measured. The next proof should be a small complete workflow on test projects, including restart, lost-response, duplicate-job, permission-revocation, and cross-tenant isolation tests. Dogfooding is sensible first against a separate noncritical Pooltune project, with the authoritative job and permission database excluded from autonomous repair. The architecture should make every decision and external effect inspectable before increasing customer count or autonomy.

## What this changes about the next decision

The main unresolved issue is no longer whether Pooltune must host customer data. It is which evidence each repair needs, which evidence can safely be retained or sent to the model, and which SQL authority can be granted without broad unnecessary access. Define that contract per repair before building a universal connector. A working, measurable Go workflow with those boundaries will teach more about the eventual scaling requirements than choosing Rust or C++ for hypothetical throughput.
