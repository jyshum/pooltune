# Give Pooltune Room to Repair Databases

**Pooltune should adapt its work to the database, inside limits authorized during setup.** It should collect lightweight measurements continuously, investigate worthwhile problems, and perform eligible repairs without repeatedly asking the customer. More expensive work gets a suitable execution budget and, where necessary, a quiet window. Tight universal limits would make useful repairs impossible; unlimited work could make the application slower. The practical design combines enforceable limits, observed resource pressure and repair-specific recovery. All six accepted repairs remain in scope. The policies and numbers below are proposals for qualification, not accepted settings or demonstrated guarantees. Research reviewed PostgreSQL 17, Supabase and framework documentation on November 12, 2026; it made no database changes or performance measurements.

## Permissions authorize work; budgets govern execution

Permission answers “may Pooltune change this table or function?” An operating budget answers “how much work may this authorized operation do, under current conditions?” Customers can grant both up front. The investigator then has room to collect relevant evidence and choose among permitted repairs. It should ask again only when the required action falls outside those grants, rather than asking before every query. This implements the accepted capability-first direction while preserving the six repair boundaries.

Three approaches are plausible. **Fixed tight limits** are straightforward to implement, but a timeout suitable for checking statistics could repeatedly abort a legitimate index build. **Maintenance-window-only repairs** reduce daytime interference, but postpone useful work and fit poorly when customers are active around the clock. **Adaptive execution within explicit ceilings**, supplemented by quiet windows for expensive operations, is the recommended compromise. It needs more engineering: fresh measurements, separate operation budgets, progress tracking and recovery. The benefit is allowing useful work to finish when conditions support it.

Some limits are directly enforceable. PostgreSQL offers statement deadlines and lock-wait timeouts; Pooltune can limit its own active jobs and model spending. Other controls are narrower than they sound. Maintenance workspace settings do not cap all process memory, and parallel-worker limits do not reserve a CPU share. **These interfaces cannot guarantee “Pooltune uses at most 5% of your CPU.”** CPU, available memory and disk pressure are observed conditions that guide admission and stopping, with sampling delay. ([PostgreSQL timeouts](https://www.postgresql.org/docs/17/runtime-config-client.html), [resource settings](https://www.postgresql.org/docs/17/runtime-config-resource.html))

Supabase recommends collecting its metrics once per minute. Its documented metrics include CPU, available memory and disk activity, but availability must be discovered for the connected project. Missing measurements mean unknown capacity. `pg_stat_statements` supplies calls, execution-time totals and block work; it does not supply per-query CPU or latency percentiles. Interval means require compatible counter differences, with resets and evictions handled. A lower CPU graph is not improvement if fewer requests completed. ([Metrics API](https://supabase.com/docs/guides/observability/metrics), [exported metrics](https://github.com/supabase/supabase-grafana/blob/main/docs/metrics.md), [statement statistics](https://www.postgresql.org/docs/17/pgstatstatements.html))

## Each repair needs a different operating envelope

The following rules describe what qualified automatic execution could do. They do not turn a diagnosis into permission, or establish that every Supabase project exposes the required evidence and privileges.

| Repair | Useful automatic work | Resource and stopping rules | What verifies the result |
|---|---|---|---|
| **Create an index** | Rank candidates from query plans, filters and existing indexes; build a justified nonunique index concurrently. | Account for permanent index size, temporary workspace, WAL and customer growth. Give the build enough time; monitor its phase and workload impact. Defer on insufficient disk space or blocking transactions. | Relevant queries do less work or complete faster, with acceptable write and storage overhead. |
| **Refresh statistics** | Analyze the affected table or columns when stale summaries explain poor estimates. | Target the demonstrated issue; use an appropriate sample, buffer strategy and execution deadline. Avoid repeatedly analyzing already-current data. | Row estimates and execution improve across relevant inputs, without new regressions. |
| **Collect richer statistics** | Add suitable extended statistics or increase selected column detail, then analyze. | Bound the extra collection detail and account for future maintenance cost. Preserve previous settings for recovery. | Improvements persist across small and large customers and the relevant column combinations. |
| **Clean old row versions** | Run targeted plain vacuum; adjust enrolled table thresholds when late cleanup is the cause. | Avoid duplicating active cleanup. Use cost-based delay and limited parallelism; avoid optional tail truncation. Defer if old transactions prevent useful cleanup. | Cleanup keeps pace, relevant table reads improve, and foreground work remains healthy. |
| **Tune function memory** | Increase an enrolled function’s `work_mem` when its internal operations demonstrably spill. | Evaluate simultaneous callers, multiple operations and parallel workers. Select the smallest useful increase within a qualified memory budget. | Temporary disk work and duration improve without memory pressure, errors or harm to other queries. |
| **Move a scheduled job** | Shift future runs of an enrolled job within approved business windows. | Preserve deadlines, dependencies, timezone and intended frequency. Inspect active and potentially queued work before a schedule transition. | Future runs finish on time and the previously affected queries improve under comparable demand. |

**Concurrent index creation still does substantial work.** It performs multiple phases and scans, permits ordinary writes, and can wait for existing transactions. Failure can leave an invalid index that still has overhead. Progress views show the current phase; there is no general pause-and-resume command. If stopped, Pooltune must inspect the result and clean up only its own qualifying object under the appropriate grant. It should not physically build dozens of candidates merely because the model proposed them. ([CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html), [progress reporting](https://www.postgresql.org/docs/17/progress-reporting.html), [DROP INDEX](https://www.postgresql.org/docs/17/sql-dropindex.html))

Statistics collection is targeted work, not free metadata editing. A higher statistics target increases sampling cost; extended statistics require a subsequent analysis and do not solve every estimate problem, including PostgreSQL 17 cross-table join selectivity. Removing an added statistics object or restoring a target does not recreate the exact previous sampled statistics. ([ANALYZE](https://www.postgresql.org/docs/17/sql-analyze.html), [CREATE STATISTICS](https://www.postgresql.org/docs/17/sql-createstatistics.html))

Plain vacuum can make space reusable and update visibility information that helps index-only scans. It is not a table rewrite. `TRUNCATE false` avoids the optional exclusive-lock attempt to return empty tail pages to the operating system. Old transactions or replication slots can prevent necessary cleanup; repeated vacuum cannot remove that underlying obstacle. V1 explains those cases rather than killing customer transactions. ([VACUUM](https://www.postgresql.org/docs/17/sql-vacuum.html), [routine vacuuming](https://www.postgresql.org/docs/17/routine-vacuuming.html))

**One active Pooltune repair does not mean one active function call.** Application traffic controls ordinary invocations. As an illustrative screening calculation, 20 callers each using two sorts at 16 MB suggest roughly 640 MB before other overhead. Hash operations and parallel execution add further demand. A faster single trial therefore cannot qualify a persistent memory increase. Unknown concurrency can defer that change while investigation continues. Restoring a function setting also does not promise to reclaim memory immediately from calls already running. ([Resource settings](https://www.postgresql.org/docs/17/runtime-config-resource.html), [function settings](https://www.postgresql.org/docs/17/sql-createfunction.html))

Cron work has a business budget as well as a resource budget. Moving a report from 01:00 to 01:30 is useful only if it still meets its deadline. pg_cron runs one instance of a given job at a time, with another due execution waiting; changing its schedule must not be described as clearing queued work. Initially qualify simple, infrequent jobs with clear windows. Do not cancel active customer jobs or skip required work to make a performance chart look better. ([pg_cron](https://github.com/citusdata/pg_cron), [scheduler task state](https://raw.githubusercontent.com/citusdata/pg_cron/main/src/task_states.c), [Supabase Cron](https://supabase.com/docs/guides/cron))

## Go enforces budgets while LangGraph investigates

The proposed loop is collection, numerical detection, investigation, execution checks, recorded action, repair and verification. Go owns resource admission, permissions, action identity and recovery. The TypeScript/LangGraph investigator chooses useful hypotheses and evidence requests. Routine monitoring needs no model call. Rich evidence access remains available within upfront grants, but repeated requests for unchanged evidence should stop.

**Maintain two separate budgets:** customer-database work and Pooltune’s own model/worker spending. An investigation can exhaust its model allowance while a database operation still requires monitoring or cleanup. Recovery therefore needs capacity independent of ordinary investigation spending. Shared limits must apply across worker replicas and customers, with backoff for provider throttling. ([Anthropic rate limits](https://platform.claude.com/docs/en/api/rate-limits), [Supabase API limits](https://supabase.com/docs/reference/api/introduction))

These are starting proposals to test, not promises about every compute tier:

| Work | Initial qualification proposal |
|---|---|
| Routine collection | Resource metrics and selected query/table deltas every 60 seconds, with staggered schedules. Refresh schema periodically and before relevant changes. |
| Lightweight SQL | One collector connection per project; begin with a 2-second statement timeout and backoff. This timeout does not apply to repairs. |
| Investigation | One active investigator per project; begin with eight model turns and twelve new evidence requests. Permit bounded extensions for named unresolved questions within an upfront spending ceiling. |
| Extra query trials | One resource-intensive trial per project at a time, with a query-specific deadline and temporary-space limits where supported. |
| Repairs | One active mutation per project initially, with separate time, storage and memory rules for each repair. Protect verification of overlapping queries before introducing another change. |

A proposed regression trigger could require three five-minute windows, sufficient calls, and both a relative and absolute slowdown. That is a signal to investigate, not proof of a cause. Important low-frequency queries need longer observation or explicit latency objectives. Persistent high total work deserves investigation even without a sudden spike. Severe errors or pressure can trigger immediate diagnosis without granting permission for an expensive emergency experiment.

Additional trials execute real work. `EXPLAIN ANALYZE` runs the statement; read-only mode and rollback do not form a complete sandbox for arbitrary function effects. Trials need representative roles, inputs and settings. Adding `LIMIT` changes the tested workload. Existing valid measurements and normal traffic should answer questions first; another experiment should resolve a specific missing fact. ([EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html), [transaction semantics](https://www.postgresql.org/docs/17/sql-set-transaction.html), [row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html))

Stopping means canceling **Pooltune’s own identified operation**, then confirming its state. It does not authorize canceling customer transactions. A lost response is an unknown outcome, not evidence that nothing happened. LangGraph retries do not make external writes exactly-once: workers must inspect whether an action completed or remains active before repeating it. Session-level controls for long Supabase administration also need a qualified direct or session-mode connection, not an assumption that every API endpoint behaves identically. ([Cancellation](https://www.postgresql.org/docs/17/functions-admin.html), [LangGraph fault tolerance](https://docs.langchain.com/oss/javascript/langgraph/fault-tolerance), [Supabase timeouts](https://supabase.com/docs/guides/database/postgres/timeouts))

## Rookery should establish evidence before stress

Rookery does not need heavy traffic for an access test. Later, data size and distribution expose scanning and planner problems; repeated executions build confidence; simultaneous callers expose contention and memory risks. Those are different test dimensions. Start with a representative dataset and repeatable queries, then increase concurrency deliberately. An already-correct query should produce a justified no-change result.

The implementation handoff should turn each repair row into a tool contract covering evidence, effects, limits, progress, stopping and recovery. Qualification must include uncertainty and interruption as well as successful repairs. The goal is a service that can explain why a repair ran now, why it waited, and whether it helped. That is how operating limits become part of agent competence rather than arbitrary restrictions on it.
