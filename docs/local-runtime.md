# Local PostgreSQL runtime

The `traffic` executable now has a real, opt-in `-local-pg-runtime PROFILE.json`
path. The ordinary unconfigured modes remain health-only. The profile is for an
isolated local PostgreSQL instance. It does not enable Azure, Google Cloud,
Supabase REST, managed AI, or the administration UI automatically.

```sh
go build -o /tmp/pooltune ./cmd/pooltune
/tmp/pooltune traffic -listen 127.0.0.1:8080 -local-pg-runtime /absolute/path/runtime.json
```

A `local-pg-1` profile supplies the explicit target/database/upstream, loopback
PostgreSQL listener, private state directory, secret root, positive epoch,
capacity/session ceilings, approved registry/guardrails/stable policy, and
scheduler ceilings. See `internal/runtime.Config` for the exact typed schema.
Unknown JSON fields and trailing documents reject. Duration fields use Go's
integer nanoseconds. There are no inferred production tuning defaults.

All certificate, private-key, CA, cohort-key and monitor-DSN references must be
absolute paths inside the configured secret root. Files must be private regular
files. The cohort key is 32 random bytes encoded as 64 hexadecimal characters.
The monitor DSN supplies credentials but cannot redirect the configured target.
Original application credentials are relayed through TLS/SCRAM; the monitor
credential is never used for application SQL. PostgreSQL clients must use the
supported unnamed, non-pipelined protocol profile and disable SCRAM channel
binding. See compatibility.md.

Before initial admission, a real monitor connection verifies visibility into
`pg_stat_activity`, no other client backends, and sufficient nonreserved physical
connection slots. This is deliberately limited to an exclusively used local test
database. It is not a proof against an external application connecting later.
Use a separate isolated instance. Neither this startup path nor the test modifies
an existing cloud database.

The runtime serves TLS PostgreSQL, a mode-0600 Unix control socket inside the
private state directory, and loopback liveness/readiness. Secret material, SQL,
parameters, and result rows do not enter admission observations. A PostgreSQL
observation covers one complete transaction or autocommit exchange. Failed SQL,
rejected admission and uncertain completion are distinct outcomes.

## Canary transitions

The rollout driver uses the existing SQLite coordinator and private control
client. It records each activation intent before applying it, reconciles unknown
ACKs without resending, and distinguishes policy, activation and capacity IDs.
Stable-policy baseline partitioning reuses compiled policies. A local HMAC key
assigns authenticated server-generated session identities to cohorts; transaction
permits retain their original binding. A nominal 10% identity assignment is not a
promise of exactly 10% measured traffic.

Each stage waits for old activation/policy bindings and excess occupancy to drain
before measurement. For 100%, a separate durable drain revision routes new traffic
to candidate while stable queued/active work keeps its old allocation. New stable
admissions are fenced, including late classifications. Final acceptance retains
active candidate permits and reclassifies its queues without extending deadlines.
A pending acceptance committed before controller restart is reconciled from the
persisted activation timestamp instead of being blindly reverted.

## Verified and still gated

Real local PostgreSQL tests cover TLS/SCRAM, preserved application identity,
transaction retention across a live 10% canary, both cohorts forwarding SQL,
new-revision rollback, the assembled runtime/Unix socket/readiness, and clean
shutdown. Workloads are generated by the tests. These are correctness results,
not latency improvement or managed-provider compatibility evidence.

Restart admission remains quarantined pending independent control-ledger,
backend-orphan and epoch evidence. Increasing the profile epoch does not bypass
that requirement. A failed initial proof also leaves the persisted state
quarantined. Do not delete state or fabricate a recovery callback to make an
existing deployment ready. Shutdown reports unresolved sessions instead of
claiming they completed.

The runtime now exposes bounded arrival-window measurements over its private Unix
socket. Arrivals retain failures, rejections/timeouts, pending and uncertain
outcomes; only successful completions enter latency histograms. Window creation
and rotation are idempotent so a retried command cannot erase bad evidence. Old
work outside the selected window remains visible to safety checks.

The local profile samples actual host CPU counter deltas and memory availability
once per second using [gopsutil v4.26.9](https://github.com/shirou/gopsutil). These
readings include other host processes and are explicitly labeled `local-host`.
They are valid only for this same-host development profile, never a substitute
for Azure, Google Cloud or Supabase database pressure. Missing/first/reset samples
remain unavailable instead of reporting zero pressure.

`RolloutDriver.ConfigureMeasurements` binds a fixed window duration and resource
source before starting an experiment. The driver reads real measured windows and
rotates them after consumption. Incomplete windows still expose live starvation
and uncertainty. A calibrated evaluation profile and the running control/agent
service are still needed for autonomous promotion. Continuous control, the bounded agent authority, real local admin reads/freeze/restore,
and opt-in local pressure reductions are now wired; see `control-runtime.md`. Opt-in ordered PG admission growth and independently anchored local PG restart
are also implemented; see controller.md and recovery.md. Local REST assembly is
documented in rest-runtime.md. Interactive onboarding, remaining capacity/recovery
profiles, container build/restart tests and G1-G5 release work remain incomplete. No additional paid model calls were made.

## Same-host ownership

Both local traffic profiles hold a shared OS-owner lock keyed by the verified
PostgreSQL system identifier. The monitor reads `pg_control_system()` and the
current database OID over the verified TLS connection; unavailable identity fails
startup. Distinct state directories, target labels, endpoint aliases and database
names cannot create a second local budget in the same PostgreSQL cluster because
`max_connections` is cluster-wide. The private lock namespace is
`/tmp/pooltune-local-owners-<uid>`, independent of TMPDIR and runtime JSON. Do not
unlink its lock files while a process might own them. Locks are released on close
or process death, but retained files are harmless. This is a single-host, single
OS-owner development boundary, not distributed fencing or an independent epoch
anchor. Multi-account, multi-host and combined-path deployments remain gated.

The opt-in PG capacity-growth and independently anchored restart paths are described
in controller.md and recovery.md. Legacy profiles without a RecoveryDirectory
continue to refuse restart. Neither path closes the full release gates.
